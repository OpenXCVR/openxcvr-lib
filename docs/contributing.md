# Contributing

How to change this repository and prove the change is sound: the check set,
schema edits, regeneration, and the rules a documentation page must meet. The
design these checks protect is in [architecture](architecture.md); focused
test loops are in [testing](testing.md).

A pull request opened on the public repository is reviewed there, then a
maintainer ports the change into the development repository. The next public
export carries it. The public history is that series of exports, not the
development history.

## Toolchain

Rust 1.82 or newer, Python 3, and — for the C binding — CMake 3.16 or newer
with a C99 compiler. Run commands from the repository root.

## The check set

```sh
cargo fmt --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
python3 tools/validate-schemas.py
python3 tools/test_validate_schemas.py
python3 -m unittest tools.test_gen_docs tools.test_check_regen_equality
```

`cargo test --workspace` includes the schema vocabulary guard and the
documentation examples. After regenerating the C binding, also build it and
run its registered tests (add `-DOPENXCVR_C_RICH=ON` for the rich variant):

```sh
cmake -S bindings/c -B build/openxcvr-c -DCMAKE_BUILD_TYPE=Release
cmake --build build/openxcvr-c
ctest --test-dir build/openxcvr-c --output-on-failure
```

## Changing a schema

1. Edit the YAML under [`schemas/`](../schemas/README.md), following its
   authoring rules.
2. Validate structure and key vocabulary. A schema edit is complete only when
   both pass:

   ```sh
   python3 tools/validate-schemas.py
   cargo test -p openxcvr-codegen --test strict_schema_vocabulary
   ```

3. Regenerate (below), review the generated diff, and commit it together with
   the schema change. Name the generator command in the commit message.

Never edit a generated file to change behaviour; the next regeneration
discards the edit and the equality check fails in the meantime.

## Regeneration

```sh
tools/regen-all.sh               # every binding surface plus the Markdown reference
tools/regen-rust.sh              # one surface; each has its own script:
                                 #   regen-{rust,python,typescript,java,
                                 #   csharp,openapi,markdown}.sh
./tools/check-regen-equality.sh  # fails when committed output differs
```

Binding regeneration scripts accept spec names (`cmis`, `sff-8636`, `sff-8472`,
and `cmis-lt-1.0` where that surface has a crate) to limit the run; none takes
a language argument. The C, Go and PHP surfaces have no script of their own and
are regenerated by `regen-all.sh`. The [generated reference](reference/index.md)
is produced by `regen-markdown.sh` from the same intermediate representation as
the bindings. With no spec names it renders every namespace that has
`schemas/<name>/_index.yaml`. `regen-all.sh` with no spec names keeps the
binding surfaces on CMIS, SFF-8636 and SFF-8472, and renders that full
Markdown set.
Where the schemas record no value it prints `not recorded`, and a
per-revision projection is not an independent qualification of a historical
specification.

## Changing documentation

Link a new page from the [documentation map](README.md) or from a page that
map already reaches, and keep every local link and anchor resolving. Open a
guide with a `# ` title and a sentence saying what the page is for.

Rust examples are tested. A page with a `rust` block is listed in
[`doc_snippets.rs`](../crates/openxcvr/src/doc_snippets.rs), and
`cargo test --doc -p openxcvr` compiles and runs it. Write each block as a
complete program with `fn main() -> Result<(), Box<dyn std::error::Error>>`.
Tag a block `rust,no_run` only when it opens a fixture by repository-relative
path. Give every fence a language tag.

```sh
cargo test --doc -p openxcvr
```

## Fixtures and goldens

New test data follows the provenance rules in the
[fixture corpus](../tests/fixtures/README.md). A
[golden output](../tests/golden/README.md) is never edited to make a test
pass: establish whether the decode or the golden is wrong first.

## What belongs elsewhere

This repository is the schemas, the generator, the bindings and the fixtures.
Kernel ABI belongs to the kernel module. Userland tools and packaging are
separate components. Version names are in [versioning](versioning.md).
Specification PDFs are not stored here; schema files cite the clause they
were transcribed from.
