# Connector locking: revised design for frontier review

**Status:** design only; no implemented guarantee, deployment or approval claimed. This revises the exclusivity story for the transports. The current per-UID hashed-path lock does **not** provide cross-UID exclusion. The host-side component owns host mutation; this library owns the unprivileged runtime checks. All locks below are cooperative, not a guarantee against software that bypasses the library.

## Boundary and interfaces

- Keep `NativeHid::open_path(&CStr) -> Result<NativeHid>`, `I2cDevBus::open(impl AsRef<Path>) -> Result<I2cDevBus>`, `Reports`, `I2cBus`, and the shared `Error`/`ErrorKind` semantics. Replace the published `DeviceLock::acquire(&OsStr)` path-key API with an opened-device guard; remove the path-key public entrypoint on Linux rather than retaining a weaker, interchangeable-looking lock. This is a named Rust crate API break (not a change to the parent bridge's ten C exports); amend the interface receipt and dependent callers together. The new guard is constructed only from an opened device descriptor and the configured trusted lock-file handle. No public constructor may synthesize a guard from a pathname alone. No VID/PID, driver, board-control, or kernel transport is introduced here. The caller continues to select the device; ambiguity is a refusal, never a first match.
- Linux: open the selected node first with read/write access and `O_CLOEXEC`, follow a caller-supplied symlink only to the **actual** character device, `fstat` that fd (reject non-character), derive the lock key exclusively from its `st_rdev`, then acquire one nonblocking exclusive OFD byte-range lock on a separate, shared, administrator-provisioned regular file. Hold both fds for the session. The i2c-dev transfer must use **that same opened adapter fd**, including `I2C_SLAVE` and `I2C_RDWR`; the current `LinuxI2CDevice::new(path, ...)` opens its own fd, so the low-level i2c-dev wrapper needs a descriptor-owning construction path or equivalent refactor. Do not open a different node after locking.
- Linux hidraw: retain the first real hidraw fd for the entire `NativeHid` lifetime. Once locked, call pinned hidapi 2.6.7 `linux-static-hidraw` `open_path` on `/proc/self/fd/N` for that retained fd (a *second* open, **not** `dup`, and not passing the original pathname). Keep its `HidDevice` and the retained fd and OFD guard together; drop HID before the guard. Before and after the hidapi open, check `fstat` on the retained fd and `stat` on the proc-fd target; validate the selected adapter/interface identity where obtainable. The **instance-continuity mechanism is the retained real hidraw open**, not a hidden-fd comparison: on supported Linux hidraw implementations, opening increments the old object's open count; disconnect marks it nonexistent, but its minor remains reserved until the last old open closes. The proc-fd reopen must therefore reach that pinned live hidraw instance or fail after disconnect, never a replacement reusing its minor. Keep the pin alive until *after* hidapi closes on success and every partial-failure path; do not allow an `O_PATH` pin. The pinned hidapi C backend does `open(path, O_RDWR|O_CLOEXEC)` and `HIDIOCGRDESCSIZE` on the opened fd; it does not accept an already-open fd. Restrict this path to kernels with the verified hidraw open-count/minor-reservation behavior (inspected Linux v6.12 and current upstream); unsupported/vendor-modified semantics fail closed until validated. `/proc` availability is required; never fall back to a pathname open. Barriers around pin open, lock acquisition, proc-fd reopen, disappearance and replug must prove no report can reach a replacement. The source-backed lifetime argument selects the design; hardware execution remains a named proof obligation, not an assertion that a live bridge has been tested.
- macOS: leave hidapi's `kIOHIDOptionsTypeSeizeDevice` default and its `kIOReturnExclusiveAccess` → `Busy` mapping intact. Do not apply Linux OFD locks or change `macos-shared-device` defaults.
- Windows: `windows-native` currently calls `CreateFileW(..., FILE_SHARE_READ|FILE_SHARE_WRITE, ...)`, so sharing violations alone cannot establish cooperating exclusivity. The proposed `LockFileEx` range must live in a **single administrator-provisioned shared file** opened under an administrator-chosen ACL allowing the authorized non-elevated users, with no per-user temp-directory fallback; the lock is held through the HID session. Canonical path string hashing is insufficient to identify device-object aliases: derive a stable device interface identity from the selected opened HID device and prove its alias/replug properties, or fail closed. Exact Windows range mapping/identity and host provisioning are unresolved; **Windows cross-compile is not runtime proof**, and no cross-UID Windows exclusivity claim is approved by this design.

## Linux namespace, mapping and provisioning

Use exactly one regular lock inode per host across both Linux transport classes. Administrators choose an absolute path under an administrator-controlled, non-user-writable parent as part of the parent's **once-per-host**, explicit administrator-run setup (`hw-breakoutboards/software/docs/portability/linux-setup.md`). The parent installer/runbook must provision this file, its ownership and a group/ACL permitting only intended connector users to open it for write, without making the parent writable by those users. It must include this state in prior-state capture, apply failure rollback, restore, and audit, beside existing udev rules for hidraw and i2c-dev. **No owner account, numeric permission mode, group name or final path is selected here**; the parent must choose and record those in its setup contract, then supply the resulting path/trust metadata to the library through deployment configuration. The library does not create/chown/chmod/truncate/remove the file, widen access, install rules, elevate, or invent a fallback at runtime. Parent setup being unperformed remains a named Linux permission gap; setup fixtures are not live access proof.

Open relative to a validated trusted parent using `O_NOFOLLOW|O_CLOEXEC` and write access (needed by `F_WRLCK`), without `O_CREAT`/`O_TRUNC`; `fstat` the opened file and verify regular type, expected administrator-controlled ownership/access policy and identity against the configured path via dirfd-relative no-follow lookup. Reject symlinks, replacement, untrusted parent, wrong owner/mode/ACL, multiple links or missing file. The parent must not replace/unlink this inode while sessions run: a new inode at the same path would split locks. Administrative migration is quiescent (below). Authorized users with write access are trusted not to corrupt/truncate the file; OFD locks do not protect against an authorized malicious writer or an unrelated application ignoring them.

**Exact Linux range:** require a Linux character `st_rdev` whose decoded `major` fits 12 bits (`0…4095`) and `minor` fits 20 bits (`0…1048575`). Compute `offset = (major << 20) | minor` in checked 64-bit arithmetic, `l_whence=SEEK_SET`, `l_start=offset`, `l_len=1`, `l_type=F_WRLCK`, `fcntl(F_OFD_SETLK)` (nonblocking). Offsets occupy `[0, 4294967295]`; end-exclusive is at most `4294967296`, safely below signed 64-bit `off_t` maximum. Require 64-bit `off_t`; fail closed on unsupported ABI, kernel, filesystem or out-of-range device numbers, rather than mask, hash, modulo, or fall back to POSIX record locks/flock. Linux character-device numbering's 12/20 kernel allocation and userspace `major`/`minor` decoding must be checked on supported target architectures. Distinct `(major, minor)` pairs have distinct bytes; hidraw and i2c-dev sharing a number correctly share a guard. Separate `mknod` aliases with equal `st_rdev` collide. Fresh opens of the lock file yield distinct open file descriptions even **in one process**, so second open conflicts; do not `dup` a guard for another session. Sessions are **not usable in a child after `fork`**. Record the creating process ID in the guard; every transfer, report and board-control entry refuses use when that ID differs from the current process, before touching the bus/HID device. The child discards inherited handles without explicitly unlocking the shared OFD; its close of inherited descriptors cannot release the parent's lock while the parent still owns its descriptor. To operate, the child must independently reopen the device and acquire its own guard (which reports `Busy` until the parent's session closes). `O_CLOEXEC` applies to device, pin and lock-file descriptors. Tests cover fork refusal, delayed child cleanup, parent ownership and final release. Closing the guard's fd releases only its OFD lock; unrelated opens/closes cannot release it. Do not mix the old `flock` and new OFD lock and claim that they mutually exclude.

## Open, error and identity rules

Check the device fd *before* acquiring the guard so absent or unpermitted nodes stay `Disconnected` or `PermissionDenied`, not `Busy` or generic I/O. A non-char target or wrong device/interface is `Invalid`/`Unsupported`; multiple candidates are `Invalid`/ambiguous. `EAGAIN`/`EACCES` from `F_OFD_SETLK` when a competing lock exists → `Busy`; access denied on the device or shared file → `PermissionDenied` with the failing resource named; missing/untrusted shared file, unsupported OFD operation, unable-to-prove identity, and broken provisioning → explicit fail-closed configuration/`Io` diagnostics, **never** `Usable` or a local fallback. Do not conflate lock permission denial with a busy device. Kernel I2C address claim `EBUSY` remains `Busy` (`KernelClient` in diagnosis); an `I2C_RDWR` error after submission keeps `write_may_have_applied`. A failure before submission does not. Host-state probing takes and releases the same range only after validating the selected real device and lock inode; inability to probe → `Inconclusive`, not `Usable`. Keep transport-specific `NoHidrawNode`, `NoI2cAdapter`, and `NotPermitted` results; a permission failure for one path never suppresses a usable other path.

A pathname is a selector, not a lock identity. Symlink/hardlink/device-node aliases converge on `fstat(fd).st_rdev`; path `canonicalize` and 64-bit FNV are removed from the security argument. The guard applies to the actually opened descriptor; a mutable pathname retargeted afterward cannot redirect its transfer fd. For HID the retained real hidraw pin plus the proc-fd reopen is the chosen continuity contract, with no fallback to the original pathname. The existing `open_path(&CStr)` and `I2cDevBus::open(path)` receive **only a path** and make no promise that it is the device previously enumerated by another call. Identity-sensitive callers instead use new, separately named open APIs that accept an **expected selection token** plus the selected path. For HID, the token contains the enumeration record's VID/PID, usage page, usage, interface number and available serial, plus the selected sysfs/hidraw instance identity when supported; `NativeHid::open_selected(path, expected)` opens and retains the real hidraw descriptor, then compares its pinned descriptor/sysfs identity with `expected` before the OFD guard and before any report. It rechecks the observable HID identity after hidapi's proc-fd reopen; missing or changed evidence refuses as `Disconnected`/`Invalid`, never falls back to path-only open. For i2c-dev, diagnosis returns an expected adapter token tying the requested vendor/product/interface, adapter sysfs ancestry and chosen node identity to the selected path; `I2cDevBus::open_selected(path, expected)` opens the transfer descriptor once, validates the descriptor's `st_rdev` and its currently bound sysfs ancestry against that token, then acquires the guard before any claim or transfer. An unplug/replug replacement with the same device number but a different sysfs instance must fail, not be treated as the original selection. Tokens are compared to independently observed opened-device identity, not to the caller's pathname or the current enumeration list alone. If the platform cannot expose enough instance identity to distinguish replacement at this first-open boundary, identity-sensitive open fails closed; it does not silently degrade to path-only semantics. Both APIs keep the generic transport free of a hard-coded MCP2221A policy. The parent bridge's `Session::open` (`session.rs:183–208`) and `Session::open_i2c_dev` (`:231–233`) migrate from resolve/enumerate + path-only open to resolve/enumerate producing a token + `open_selected`; they still verify the board profile and remain read/write uncertainty aware. Path-only constructors remain available only with their explicitly weaker caller-selected-path contract; they are not used by the parent for an earlier device selection. Deterministic tests replace A with B between selection and first open (including reused path/minor and matching VID/PID but distinct instance identity): no report or I²C transfer reaches B, and the open refuses. HID continuity across the later second open separately follows the retained-real-hidraw-fd lifetime rule above on supported kernels, not a public hidapi raw-fd accessor. `st_rdev` is a **host-local lifetime key**, not a persistent physical-device identifier. Hold the range until all transfers and backend handles are gone; a replug may reuse a minor, and a still-open old session must block the new one until retired. On disconnect invalidate paged selection and report `Disconnected`; never auto-retarget or retry uncertain writes. Exact continuity against an instantaneous same-minor replacement remains a proof obligation, not an implicit guarantee.

## Migration and verification obligations

Cut over only with all prior connector sessions stopped: parent administrator provisions the trusted shared inode, verifies two intended UIDs can open it, freezes old sessions, deploys all cooperating clients to the new protocol, then starts them. A mixed old per-UID `flock` client and new OFD client **can both acquire**, so no rolling concurrent migration. Keep the old namespace only as inert historical state; do not remove an in-use inode. Rollback likewise requires draining sessions and restoring the prior coherent version/provisioning; record the chosen inode and validation result. No deployment is part of this document.

Hardware-free test matrix (synthetic second adapter profile as well as MCP2221A, without vendor captures): two UIDs contend for the same range through independent processes; second independent open **in the same process** returns `Busy`; separate device nodes with equal `st_rdev` collide; different minors and different majors do not; boundary `(4095,1048575)` maps to `4294967295` and overflow is rejected; symlink/hardlink aliases collide; removing/replacing the lock inode is detected/fails closed; absent, unpermitted and non-char nodes classify separately; inaccessible `/proc`, failed hidapi second open, identity mismatch and unplug/replug refuse safely; i2c transfers use the fd originally keyed; forced close/drop releases the range; POSIX `flock`/OFD mixed-version test demonstrates the migration hazard. Cross-UID tests require a deliberately provisioned test file and two authorized test UIDs, not an assumed account. Fake sysfs proves decisions, not real udev permission or hardware ownership. macOS seize and Windows `LockFileEx`/ACL need platform execution evidence; no Windows runtime execution is claimed by the frozen goals.

**Unresolved, for the host-side component:** (1) parent-approved shared-file path, ownership/ACL/group, installer/restore and live cross-UID permission proof for both node classes; (2) exact descriptor-owning i2c-dev construction API and coordinated removal of the public path-key `DeviceLock::acquire(key)` API (name that break in a revised receipt); (3) implement and test the selected retained-real-hidraw-fd lifetime rule on supported kernels, including proc-fd reopening, partial-open cleanup and rapid replug; if the kernel's minor-reservation rule cannot be established, fail closed rather than narrow the frozen wrong-target guarantee; (4) Windows shared-file ACL, device-object identity and range mapping plus Windows-host tests; cross-compile alone cannot clear this; (5) supported Linux architecture/off_t bounds and tests for OFD support on deployed filesystems. No item above is silently resolved by the present receipt.

**Sources inspected:** the transport implementations `exclusive.rs`, `hid.rs`, `i2cdev.rs` and core `linux_i2c.rs`; the pinned hidapi 2.6.7 Linux backend (`hid_open_path` opens a new fd) and its Windows `CreateFileW`; and the local Linux `F_OFD_SETLK` header. These are the existing mechanisms; none provides the proposed cross-UID, alias-safe contract as shipped.
